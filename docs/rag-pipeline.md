# RAG 检索管道设计

> 本文描述的是 `app/rag/` 下真实生效的行为，不是设想中的目标态。

## 一、分层与职责

检索层只回答一个问题：给定一句提问，返回最可能含有答案的若干原文片段，并给出可回查的位置。
它不认路由、不拼提示词、不调用大模型，因此可以脱离 Agent 单独评测。

四层依次是：切分 → 嵌入 → 向量库 → 重排。任何一层换实现，上层的接口都不变。

## 二、切分层：按结构切，不按字数切

固定窗口切分会把代码块和表格拦腰截断，检索出来是一段读不通的残片。这里把 Markdown 的
一到六级标题、围栏代码块、连续表格行都当作硬边界，块内再受 400 字符约束，跨块用 60 字符
重叠兜底。

三个细节决定了切片质量。第一，只含标题的幽灵片段会被并入紧随其后的正文块——否则检索会
命中一个只有十几个字的标题，里面一条正文都没有。第二，重叠回退出来的起点会前移到最近的
句子边界（换行、句号、问号、感叹号、分号），不会从半个词开始。第三，若已经在换行处干净
断开，就不再叠加重叠，避免产出几十字的碎片。

强制不变量是 content[char_start:char_end] == chunk.text。它由单元测试守护，也是引用能回
原文高亮的前提：只要偏移和文本对不上，前端高亮就会错位。

块长 400、重叠 60 不是随手取的。bge-small-zh-v1.5 的上下文是 512 token，中文接近一字一
token，留出余量是为了避免 tokenizer 静默截断尾部——截断不会报错，只会让向量少掉最后一句，
召回莫名其妙地变差。

## 三、嵌入层：ONNX 优先，hashing 兜底

生产路径用 fastembed 加载 BAAI/bge-small-zh-v1.5，输出 512 维向量，权重约 90MB。选 ONNX
而不是 sentence-transformers 的理由很实际：后者会拖进整条 torch 依赖链，冷装几百 MB、十几
分钟；fastembed 只复用 onnxruntime，同一个模型在 512 维下语义效果一致。

降级路径是 hashing，384 维、零依赖、完全确定性。它不是语义模型，只是把字符 n-gram 哈希到
固定维度，够 CI 和离线环境跑通链路，但同义词检索会失效。缺包或模型不可用时自动降级为
hashing，而不是让服务起不来。

模型权重从 hf-mirror.com 下载。HF_ENDPOINT 在 config.py 里用 setdefault 兜底设置，因为
huggingface_hub 在 import 时就把这个值读成常量，晚设置无效。镜像站不支持 XET 协议，所以
同时要设 HF_HUB_DISABLE_XET，否则会先失败一次再回退。

前缀策略按模型族区分：e5 系列必须加 query 与 passage 前缀，bge-zh-v1.5 官方说明无需前缀，
所以配置里默认留空。加错前缀不会报错，只会让向量空间偏移，属于最难查的一类问题。

真实嵌入是 CPU 密集的同步调用，必须经 asyncio.to_thread 丢到线程池。在事件循环里直接
encode 会阻塞整个进程，SSE 流式期间表现为 token 突然卡住。

## 四、向量库层：集合版本化与确定性 id

Chroma 用 PersistentClient 落盘，距离空间是 cosine，检索时把 distance 换算成 1 减 distance
作为相似度分数。

集合名内嵌 embedding 的 provider、model 与维度，例如
kb_documents_fastembed_baai_bge_small_zh_v1_5_512。换模型就换了向量空间，往旧集合里塞新
向量不会报错，只会让召回悄悄变差；维度不同时 Chroma 抛 InvalidDimensionError 还算好的，
更糟的是维度相同但语义空间不同的模型混在一起。

构造集合时写入 embedding_dim 元数据，作为维度守卫：已存在的集合若记录了不同维度，启动期
立刻抛错，而不是等到写入时才发现。写入前还有一道校验，向量长度与集合维度不一致直接拒绝。

chunk_id 用 sha1 对 document_id、index、text 三者拼接后取哈希，不用 uuid4。相同内容必须
落同一个 id，否则重跑一次摄入就是一份重复数据；确定性 id 配合 upsert 让摄入天然幂等，只有
在文档内容变更时才需要 --force 先删后建。

Chroma 的匿名遥测必须在 import 之前关闭——它导入时就会读这个开关，晚了关不掉，离线环境下
会持续报错刷屏。另外 Chroma SDK 是同步的，所有调用统一丢线程池并带超时。

进程内实现负责兜底：数据落在 data/memory_store.json，重启不丢演示数据。切换 Qdrant 或
Pinecone 只需新增一个实现并改工厂函数，retriever 与 ingest 都不受影响。

## 五、重排层：把含答案的片段顶上来

向量召回的通病是语义近似但不精确：问为什么禁止硬编码 LIMIT，召回的第一名可能是一段讲
SQL 安全的泛泛之谈。lexical 重排用三项融合打分：

- 0.55 乘以向量余弦相似度
- 0.35 乘以查询词项覆盖率，即查询 token 有多少比例出现在片段里
- 0.10 乘以整句短语命中，即原句是否作为连续子串出现

覆盖率这一项是压掉长段落的关键：一段 400 字什么都谈的段落，向量分可能不低，但只覆盖了
提问里三分之一的词，融合后自然掉下去。重排是纯 CPU 的字符级运算，毫秒级，不需要线程池。

可选 cross-encoder（bge-reranker-base）精度更高但更慢，需要 sentence-transformers；配置
切过去失败时自动回落到 lexical，不会影响可用性。

默认粗召回 8 条、精排保留 3 条。3 条是上下文成本与信息完备性的折中：再多会把无关段落塞进
提示词，稀释模型注意力，也让引用变多、忠实度更难判断。

## 六、索引自检与重建

启动期的自检不是看库里有没有文档，而是比对数据库台账的切片总数与向量库的实际条数。原因
很直接：换了 embedding 模型后集合名会变、新集合是空的，而数据库里文档明明还在——旧逻辑
会静默跳过，结果是「有文档但一条都检索不到」这种最难排查的故障。

两者不一致就触发全量重建：清空集合、按当前配置重新切分与嵌入、回写切片数。单篇文档入库
失败不会中断整批，结束时再统一报告失败清单。
