# 部署、运维与配置

## 一、一键启动

docker compose up 拉起三个容器：api、postgres、redis。api 用多阶段构建，运行阶段只带
运行时依赖、以非 root 用户启动；启动脚本先执行数据库迁移建表，再拉起 uvicorn。健康检查
串成依赖顺序：postgres 与 redis 就绪后 api 才开始启动，避免「数据库还没起来，迁移先失败」。

首次启动会灌入四篇演示语料，让新 clone 的仓库零配置就能问出东西。只想看自己 docs 目录的
内容时，把灌演示语料的开关设为 false，索引一致性检查仍然会跑。

## 二、配置分级

配置全部走环境变量，示例文件里只有占位符，真实的 .env 被 gitignore 排除。

上线前必须改的有两项：SECRET_KEY 换成 secrets.token_urlsafe(48) 生成的随机值，否则 JWT
可被伪造；自动建表开关设为 false，改由 Alembic 迁移管理表结构，否则启动期自动建表会和
迁移脚本打架。

可以留空的有两项：Redis 地址留空则自动降级为进程内存缓存与限流，本地开发不需要外部
中间件；缓存强制开关默认 false，设为 true 后 Redis 不可用会直接启动失败，适合生产环境
强制依赖外部缓存。

## 三、超时预算

超时分四档，不能混用。工具调用默认 10 秒，约束的是向量库与数据库这类确定性 I/O。检索
链路单独给 15 秒，因为首次可能触发模型加载。模型加载给 600 秒，首次要下载 90MB 权重，
复用 10 秒会直接失败。正文生成给 90 秒，长答案确实需要时间；意图分类只给 20 秒，短任务
超时就回落规则路由。

复用同一个超时是最容易犯的错：把正文生成也压到 10 秒，长答案会被拦腰截断，用户看到半句
话；反过来把模型加载也放宽到 600 秒，数据库卡死时请求会挂十分钟。

## 四、冷启动与缓存目录

首次构造真实模型客户端要八秒左右：import 语言层适配库占 4.7 秒、SDK 客户端初始化 3.5 秒、
tiktoken 下载 BPE 词典 4.7 秒。这段成本若落在第一个用户请求上，首字节延迟会从 2.4 秒
变成 9 秒。

解决办法是启动期预热：打一次只生成一个 token 的请求，把建连、DNS、TLS 握手、连接池
初始化全部提前付掉。预热失败不阻断启动——网络抖动不该让服务起不来。

tiktoken 的 BPE 词典默认落在系统临时目录，容器一重启就没了、要重下。用环境变量把它固定
到项目数据目录，配合卷挂载，冷启动只付一次成本。embedding 权重同理，缓存目录指向
data/models 并挂卷复用。

## 五、健康检查

存活探针不碰任何外部依赖，只证明进程还在，用于容器重启判定。健康检查端点则逐项报告
数据库、向量库、缓存、大模型四个依赖的状态，任一降级时整体标记为 degraded，但 HTTP
状态码仍是 200——它探测的是能不能降级服务，不是是否完美。

这个区分很重要：把外部依赖写进存活探针，Redis 抖一下就会触发容器重启，雪崩就是这么
开始的。

## 六、限流与资源保护

限流按用户维度每分钟 30 次，计数存在 Redis，连不上则退化为进程内存计数——单实例够用，
多实例会各自计数，这是明确接受的取舍。SQL 执行层有 200 行的硬上限，防止一条没有 limit
的查询把内存打爆，同时把截断标记如实回报给上层。

## 七、受限网络下的交付

github.com 的 443 端口直连超时、代理对 github 返回 502，但 ssh.github.com 的 443 端口
TCP 是通的。把远端地址改成 ssh 协议加自定义端口就能推送，完全不走 HTTP 代理。代价是
需要把公钥加到 GitHub，收益是配置文件里不再有明文访问令牌。

排查顺序建议按 DNS 解析、直连、系统代理、备用端口走，不要一上来就怀疑凭据。这次实际踩
的坑就是只测了浏览器（走系统代理）就断定网络通，而 git 并没有走代理。
